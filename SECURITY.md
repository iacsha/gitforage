# Security policy

## Reporting a vulnerability

Please report privately through GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**. Do not open a public issue for a security problem.

Include what you found, how to reproduce it, and the version or commit. You will get an acknowledgement, and a fix or a decision, as quickly as a small project can manage. Reporters are credited unless they prefer not to be.

## Supported versions

gitforage is pre-1.0. Only the latest commit on the default branch gets fixes.

## Threat model, in brief

**Untrusted repo text.** Everything gitforage shows comes from repositories anyone can create: names, descriptions, topics, release tags and user logins. A hostile repo could try to inject markdown or HTML into a digest, spoof text with bidi characters, drive a terminal with escape codes, plant a `javascript:` link, or use a crafted name to reach odd API paths or file paths. Mitigations:

- Repo names must be plain `owner/repo` (`[A-Za-z0-9_.-]`, not `.` or `..`). Others are dropped on intake, and API paths are only built from validated names.
- Control, bidi and zero-width characters are stripped, and text fields are length-capped.
- Markdown output escapes markdown and HTML control characters.
- The only links emitted are `https://github.com/<owner>/<repo>`, rebuilt from the validated name. URLs in API bodies (`html_url`, `homepage`) are never used as links.
- Cache files are named by a SHA-256 hash of the request URL, never by repo names.
- The revival radar reads an upstream's homepage and description only to test whether they name the fork (compared against the validated fork name); only that yes or no is kept. Its field note is built from counts, dates, booleans and an allow-listed topic, never from either repo's text.
- Response bodies are capped at 8 MB, items per source are capped by `limits`, and the candidate pool is capped at 5,000.
- README and description text only ever becomes lowercase `[a-z0-9+#-]` tokens for the interest profile. Only those tokens are put into search queries, quoted, and they are never rendered as markup.
- Exclusion regexes from the config run against repo text, so patterns over 200 characters, with backreferences or lookarounds, or with nested quantifiers such as `(a+)+` are refused at load time. Matched text is length-capped.

**Your config file.** `interests.yml` is data. It is parsed with the YAML core schema: no custom or language tags, no merge keys, and a low alias limit against expansion attacks. Files over 256 KB are refused. Nothing in it is executed or imported, and gitforage runs no shell commands.

**Tokens.** The GitHub token comes from `GITHUB_TOKEN` or `GH_TOKEN`. It is sent only to `api.github.com` in the `Authorization` header. It is never written to the cache, state or output, and it is redacted from error messages and logs. Use a token with no scopes (public data needs none). In the scheduled workflows, the repo's own `GITHUB_TOKEN` is enough.

**State and feedback files.** `state/seen.json`, `state/stars.json`, `state/catalog.json`, `state/revival.json`, `state/early-finds.json` and `feedback.yml` are validated entry by entry when read (`state/revival.json` again at site build time: plain `owner/repo` names, counts, ISO dates, booleans, a topic slug and a cleaned, capped release tag; no URL fields). `feedback.yml` is parsed with the safe YAML core schema with aliases off and a 1 MB cap, and every mark must have a plain `owner/repo`, `keep` or `skip`, a `YYYY-MM-DD` date and well-formed topics. Bad entries are dropped and reported, and a file with problems is never rewritten. `haul.txt` (owner notes for The Haul) is read as plain text, capped at 64 KB; only `NNN: text` lines are used, and each note is cleaned of control and bidi characters, capped at 280 characters and escaped like repo text.


**Early finds (`early_finds.enabled`, off by default).** `gitforage early-finds` reads two sources that are not the GitHub API: the GitHub Trending page (HTML from `github.com/trending`) and the Hacker News front page through the Algolia API (`hn.algolia.com`). Both are untrusted input. Each request has a 30-second timeout and a 4 MB cap and carries no token (the token goes only to `api.github.com`). From Trending only `href="/owner/repo"` values in the repo headings are read, and each must pass the plain `owner/repo` check; anything else is dropped, and at most 100 names are kept. From HN only a story's URL (matched against `https://github.com/<owner>/<repo>` and the same name check), its time, id and points are read; the URL, title and text are never kept or shown. Only repos the portal itself has shown (from `state/seen.json`) are tracked, and star lookups go through the GitHub client like every other API call, built only from validated names. `state/early-finds.json` holds names, ISO dates and bounded counts only, and is validated entry by entry when read and again at site build time (bad entries are dropped and reported, and the file is capped at 16 MB). The Found early page links each repo only through the rebuilt `https://github.com/<owner>/<repo>` URL and adds nothing to the Content-Security-Policy. The daily workflow has `contents: write` only, like forage, and commits only `state/early-finds.json`.
**The portal.** Pages are static HTML built from digest files that are validated again at build time. Every page carries a Content-Security-Policy meta tag: `default-src 'none'; style-src 'self'; script-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'`. GoatCounter's script origin and endpoint are added only when analytics are configured, and its script is pinned by a subresource integrity hash. There is no inline script, inline style or style attribute. The two scripts (`theme.js`, loaded blocking in the head so the saved theme applies before paint, and `site.js`, deferred) are same-origin files. They read and write only the `gitforage-theme`, `gitforage-lang`, `gitforage-density`, `gitforage-fields` and `gitforage-sort` keys in `localStorage`, inside `try`, accept only the known values from them, and set attributes and text, never markup. Sorting and filtering compare values read from `data-*` attributes; nothing read from the page is used to build a selector or markup. A card's `data-lang` is taken from a fixed allow-list of language codes, and anything else becomes `und`. Its other `data-*` values are source names from a fixed list, topics matching `^[a-z0-9][a-z0-9-]{0,49}$`, and numbers formatted by the build, so a hostile digest can only ever produce `0`. A test checks every `data-*` attribute name on every page against an allow-list. All dynamic text goes through one HTML escaper (the page templates apply it to every value), which strips control and bidi characters and escapes `&`, `<`, `>`, both quotes and the backtick. Every `href` passes a check that allows only `https://github.com/<owner>/<repo>` links rebuilt from validated names, the project link, and relative links inside the site. The Atom feeds (`feed.xml` and `haul/feed.xml`) have their own XML escaper; the Haul feed's HTML content is built with the HTML template first and then XML-escaped as a whole. Open Graph tags hold only escaped titles and descriptions, and absolute URLs built from the validated `site.url` and the page's own path; the social card is a committed PNG, served from the site itself. Tests feed hostile descriptions (`<img onerror>`, `<script>`, `javascript:`, quote-breaking attributes, bidi overrides) through the whole build and check the output is inert.

**Personalization (`site.personalize`, off by default).** This adds the only code that builds page content in the browser, and the only network call a visitor's browser makes beyond the page itself. The surface and its mitigations:

- *The CSP.* Only the Discover page, and only when personalization is on, adds `connect-src 'self' https://api.github.com`. `'self'` lets the page read its own `catalog.json`; GitHub's API is for the visitor's stars lookup. Nothing else is added: no `unsafe-inline`, no `unsafe-eval`, no other origin. A test checks the policy on every page with the feature on and off.
- *`catalog.json`.* Built from `state/catalog.json`, which is validated entry by entry at build time like a digest: plain `owner/repo` names only, topics from the configured catalog only, text cleaned of control and bidi characters and capped, numbers range-checked, no URL fields at all. The file is capped at 2,500 items and a 1.6 MB budget. The browser validates it again (`personalize-core.js`: shape, a 4 MB cap, the same allow-lists) before using any of it.
- *Building cards.* `personalize.js` creates every node with `createElement` and puts every string in with `textContent`. Attributes go through one function that accepts only a fixed list of names, and an `href` must match `https://github.com/<owner>/<repo>` (or the portal's new-issue page) rebuilt from validated names. A test scans every script under `packages/site/assets/` and fails on `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval(`, `Function(` and similar sinks.
- *The URL.* `?t=` and `?pack=` are read with `URLSearchParams`, capped in length, and kept only when they name catalog topics or pack ids. The address is rewritten with `history.replaceState` from the validated selection only.
- *`localStorage`.* Three more keys: `gitforage-picks`, `gitforage-marks` and `gitforage-stars`. Each is read inside `try`, size-capped, parsed as JSON and schema-checked; anything that does not fit is ignored or removed. Marks are capped at 500 entries.
- *The patch file.* Export builds `gitforage-patch.json` in the browser and saves it through a `blob:` link the page made itself (the attribute allow-list accepts only this page's own `blob:` URLs and only that file name); the CSP is unchanged. Import reads one local file the visitor picks, refuses anything over 64 KB, and accepts only the exact shape Export writes: the kind marker, version 1, a date, at most 40 unique catalog topics, a catalog pack id or null, and at most 500 marks keyed by plain `owner/repo` names, each exactly `{ mark, topics, language }` with checked values. Any problem rejects the whole file with a plain message, so nothing is half applied. Imported marks lay over local ones, still capped at 500.
- *The stars lookup.* The username must match GitHub's login pattern `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,38})$` before any request, and is URL-encoded into `https://api.github.com/users/<name>/starred?per_page=100&page=N` (at most 3 pages). The request carries no credentials and no referrer. Each response must be a JSON array of at most 100 objects, under 3 MB; only each repo's `topics` are read. 404, 403 and 429, other errors and network failures get fixed messages. The username is never stored; only derived topic weights and a date are, in the browser.
- *Privacy.* Picks, marks and the stars result never leave the browser. The one outside call is the stars lookup, made by the visitor's browser to GitHub when they ask for it; gitforage has no server to receive anything. With analytics on, pack and topic picks are sent to GoatCounter as fixed event names over catalog slugs (`pick-topic-hl7`), never a username or free text.
- *Without JavaScript* none of this runs, and the server-rendered digest is the whole page.

**Visitor feedback.** The Keep and Skip buttons open a prefilled issue on the portal repo, with the title URL-encoded from a validated name. Issue text is untrusted input. `gitforage feedback`:

- accepts only a title of exactly `keep: owner/name` or `skip: owner/name` (`^(keep|skip): [A-Za-z0-9_.-]{1,39}/[A-Za-z0-9_.-]{1,100}$`), and reads nothing else from the issue;
- ignores bots, and visitor accounts younger than `feedback.min_account_age_days` (30 by default; an age that cannot be checked counts as too young);
- limits each visitor to `feedback.max_per_user` marks per run and per UTC day;
- lets visitors mark only repos the portal has listed (no API call is made for them), and takes topics and language from the digest, never from the issue;
- records owner and visitor marks separately: a visitor mark weighs `feedback.visitor_weight` (0.25) and cannot hide a repo;
- replies with fixed text and the validated name only, never the issue's title or body.

**The workflows.** Every action is pinned by a full commit SHA, and gitforage by a full commit SHA that the workflow verifies after checkout; dependencies install with `--frozen-lockfile` against the committed `bun.lock`. Top-level permissions are empty, and each job asks only for what it needs (forage and early-finds: `contents: write`; deploy: `pages: write`, `id-token: write`; feedback: `contents: write`, `issues: write`). There is no `pull_request_target`. Checkouts use `persist-credentials: false`, so the token is not in `.git/config` while gitforage runs; it is passed to `git push` for that one command. No `${{ }}` expression appears inside a `run:` script: the issue event is read from `$GITHUB_EVENT_PATH` and open issues from a JSON file, and only fixed values (the default branch name, the token) go through `env:`. A test suite checks these rules on every workflow in the repo.
